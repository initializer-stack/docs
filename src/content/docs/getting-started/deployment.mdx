# Helm PR 머지 후 배포 확인하기

“PR을 머지했는데 아직 이전 버전이 보여요.” 이때는 **어느 단계까지 새 버전이 도착했는지** 확인합니다. 아래에서는 템플릿의 `notes` 서버에 새 이미지를 배포하는 상황을 예로 듭니다.

initializer-stack의 기본 CI는 코드와 계약을 검사하고, `pnpm stack`은 로컬에서 이미지를 빌드하고 스모크 테스트를 실행합니다. 운영 배포 대상은 프로젝트에서 정합니다. 이 가이드는 새 이미지를 레지스트리에 올렸고, 운영 환경에 Helm과 Argo CD를 연결한 경우에 적용합니다. [템플릿의 기본 범위](/introduction/) · [로컬에서 처음 실행하기](/getting-started/first-run/)

## 배포 한 건 따라가기

<DeploymentFlow />

| 단계 | 어디서 무엇을 확인하나 |
| --- | --- |
| 1. Helm PR을 squash merge | 운영 환경에 적용되는 values의 `notes` 이미지 태그 또는 digest를 기록합니다. 머지 후 대상 브랜치에 생긴 **squash 커밋 SHA**가 Argo CD에서 찾을 기준입니다. |
| 2. Argo CD 동기화 | 운영 Application에서 대상 저장소·브랜치·경로를 확인합니다. 동기화 이력에서 해당 SHA 또는 그 변경을 포함한 후속 커밋이 성공적으로 적용됐는지 봅니다. |
| 3. Deployment 롤아웃 | Application의 리소스 트리에서 `notes` Deployment를 열어 Pod 템플릿의 이미지가 PR과 같은지 봅니다. 새 ReplicaSet의 Pod가 Ready가 되고 원하는 수만큼 교체됐는지 확인합니다. |
| 4. 실제 요청 확인 | 운영 서비스 주소로 읽기 요청 한 건을 보냅니다. 이번 릴리스에서 바뀐 응답이나 서비스가 제공하는 빌드 식별자로 버전을 확인합니다. 응답만으로 구분하기 어렵다면 요청 ID를 로그에서 찾아 처리한 Pod의 이미지와 대조합니다. |

## 사례 1 · 머지는 끝났고 동기화를 기다리는 중

**단서**　Helm PR에는 새 이미지가 보이는데, Argo CD의 마지막 성공 동기화는 이전 커밋이고 Deployment에도 이전 이미지가 남아 있습니다.

**확인**　Application이 어느 커밋과 비교 중인지 봅니다. 이전 커밋이면 운영 브랜치와 경로를 다시 확인합니다. 새 커밋을 인식했고 `OutOfSync`라면 차이 보기에서 이미지 변경을 찾고 동기화 이력을 엽니다. 실행 전이면 자동 동기화 설정이나 예정된 수동 반영 시점을 확인합니다. 이미 실행에 실패했다면 해당 작업의 오류가 조사 출발점입니다.

## 사례 2 · 동기화는 끝났고 새 Pod가 준비 중

**단서**　새 커밋의 동기화가 성공했고 Deployment에도 새 이미지가 들어갔지만, 새 ReplicaSet의 Pod가 `Ready=False`입니다. 롤링 배포 중에는 준비된 이전 Pod가 계속 요청을 받을 수 있습니다.

**확인**　리소스 트리에서 **새 ReplicaSet 아래의 Pod**를 열고 Events를 봅니다. `ImagePullBackOff`이면 PR에 적힌 이미지 주소와 레지스트리 접근 권한을 확인합니다. 컨테이너가 실행 중인데 readiness probe가 실패하면 이벤트에 나온 실패 사유와 같은 시각의 애플리케이션 로그를 대조합니다. 새 Pod가 Ready가 되면 롤아웃 완료와 실제 요청을 차례로 확인합니다.

두 사례 모두 상태와 로그를 조회하면서 진단할 수 있습니다. 운영 서비스 중지가 필요하면 영향 대상·이유·예상 중단 범위를 설명하고 명시적인 승인을 먼저 받습니다.
